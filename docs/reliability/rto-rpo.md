# Recovery Objectives: RPO & RTO Specifications

**Application:** Studio Lumina — Production Photography SaaS  
**Phase:** 37 (Backup, Disaster Recovery & Data Resilience)  
**Standard:** Enterprise Service Level Management, ISO/IEC 27031 Business Continuity  

---

## 1. Definitions & Framework

- **Recovery Point Objective (RPO):** The maximum acceptable age of files or database records that must be recovered from backup storage for normal operations to resume if a system failure occurs. (Essentially: *How much data loss is tolerable?*)
- **Recovery Time Objective (RTO):** The maximum acceptable duration of time and service level within which a business process or platform capability must be restored after a disaster or outage. (Essentially: *How long can the system be down?*)

---

## 2. Recovery Objective Matrix by Subsystem

| Subsystem / Data Tier | Target RPO | Target RTO | Failure Scenario Addressed | Operational Recovery Mechanism |
| :--- | :--- | :--- | :--- | :--- |
| **PostgreSQL / Neon Database** | **< 1 hour** (Scheduled) / **< 1 minute** (WAL PITR) | **< 30 minutes** | Server loss, database corruption, errant migration, dropped tables | Neon continuous WAL point-in-time recovery or restore from daily encrypted logical snapshot. |
| **Cloudflare R2 Media Storage** | **Near Zero** (Provider Durability) | **< 15 minutes** | Network partition, DNS/domain misconfiguration, accidental key rotation | Multi-AZ erasure coding across Cloudflare edge; update CDN/storage credentials or DNS records. |
| **AI Biometric Face Search** | **Regeneratable** (Zero data loss if originals exist) | **< 2 hours** (Re-indexing 5,000 photos) | Corrupted `face_embeddings` table, lost vectors, or AI microservice crash | Worker re-indexes original photos from R2 via OpenCV YuNet + SFace pipeline. |
| **Worker Processing Queues** | **< 5 minutes** | **< 10 minutes** | Worker process crash, OOM exception, machine reboot | Distributed lease timeout reaps stale jobs; BullMQ / SQL queue automatically re-dispatches pending jobs. |
| **Web Frontend & API Server** | **N/A** (Stateless code) | **< 10 minutes** | VPS destruction, container crash, OS corruption | Re-deploy from GitHub repository using PM2 / Docker / automated deployment script. |
| **Guest Biometric Selfies** | **N/A (Zero RPO)** | **Immediate** (Next guest request) | Worker timeout during face search | Guest re-captures or re-uploads selfie. Biometrics are deliberately never retained or backed up. |

## 3. Data Loss & Recoverability Analysis

### 3.1 What Data CANNOT Be Lost?
- **Original Client Photographs & Videos:** Irreplaceable moments captured by the photographer. Protected by Cloudflare R2's 11 9's durability and the 30-day Recycle Bin grace period.
- **Event Configuration & Client Metadata:** Event dates, client contact information, custom watermarks, privacy settings, and folder categorizations. Protected by daily database backups and Neon WAL streaming.
- **Photographer Account & Credentials:** Studio profile, bcrypt password hashes, and system settings.

### 3.2 What Data CAN Be Lost (Without Catastrophic Impact)?
- **Transient Guest Session Tokens:** In the event of a database failover, active guest PIN sessions may expire, requiring the guest to re-enter the 4-digit PIN once.
- **Processing Job History:** Completed or archived job logs in `processing_jobs` older than 7 days can be pruned without affecting active media.
- **Cached ZIP Archives:** Temporary ZIP files created for guest bulk downloads expire in 24 hours anyway and can be re-generated on demand.

### 3.3 What Data CAN Be Regenerated?
- **Thumbnails & Web Previews:** If preview files in R2 are corrupted or lost, the background image worker re-reads the untouched original files and generates optimized 400px and 2048px WebP files.
- **Face Embeddings:** 128-D vector records stored in `face_embeddings` can be completely regenerated by passing original photographs through YuNet and SFace models.
- **Video Posters & Transcodes:** 1080p WebM/MP4 transcoded derivatives can be regenerated by running FFmpeg on the original video stream.

## 4. Recovery Time Milestones (Emergency Timeline)

In the event of a **Total Application & Database Outage**:

```
T + 00:00 ── Outage detected by automated health checks or monitoring probe
T + 05:00 ── Incident Commander establishes containment; verifies storage & DB state
T + 12:00 ── Database restored from latest WAL point or daily logical snapshot
T + 18:00 ── API and Python AI worker microservices launched on VPS / container host
T + 22:00 ── Storage consistency audit executed; R2 connectivity verified
T + 26:00 ── Automated end-to-end smoke tests pass (Login, Gallery View, Face Search)
T + 30:00 ── Traffic re-routed to production; service fully restored (RTO Met)
```
